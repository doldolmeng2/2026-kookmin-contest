# drive_eval — 스택 주행을 녹화본과 대조해 채점한다

`rosbag2_2026_08_13-13_33_23` 같은 수동 주행 bag 에서 **상황(센서)만** 꺼내
xycar_ws 스택에 물리고, 스택이 만들어낸 **조향각 · 모드 전환 · 라바콘 주행**을
같은 bag 이 남긴 기록과 대조한다.

bag 의 `/joy`, `/xycar_motor`, `/commands/*` 는 사람이 조이콘으로 만든 값이다.
이 값들은 **입력으로 재생하지 않는다** — 채점 기준으로만 쓴다. 재생했다면 스택은
아무것도 판단하지 않고 사람의 조작을 따라가기만 했을 것이다.

```
bag ──(/scan, /resized_image, /xycar_ultrasonic, /image_raw, /camera_info)──▶ 스택
                                                                              │
bag ──(/xycar_motor 조향각, /scan 라바콘)────────── 채점 기준 ◀──(/mode_info,
                                                                /xycar_motor)─┘
```

## 한 번에 돌리기

```bash
ros2 run drive_eval run_stack_eval.sh
```

`module_drive_bag_test.py` 로 스택을 띄우고, PIDNet·YOLO 워밍업을 기다린 뒤,
센서 토픽만 `--clock` 과 함께 재생하고, 스택 출력을 별도 bag 으로 기록하고,
마지막에 `drive_eval evaluate` 를 돌려 리포트를 남긴다.

환경변수로 조절한다.

| 변수 | 기본값 | 뜻 |
|---|---|---|
| `BAG` | `~/my_rosbag/rosbag2_2026_08_13-13_33_23` | 원본 bag |
| `OUT` | `~/drive_eval_runs/run_<날짜>` | 실행 결과 디렉터리 |
| `PROFILE` | `0` | `test_profile` (0 = race, production 초기화 경로) |
| `MODE` | `0` | `main_node` 초기 모드 (0 = WAIT_GREEN) |
| `START_OFFSET` | `0` | 재생 시작 위치 [s] |
| `DURATION` | `0` (끝까지) | 재생 길이 [s] |
| `WARMUP` | `50` | 추론 노드 워밍업 대기 [s] |

### ⚠ `mode:=0` 이 아니면 한 바퀴 일찍 끝난다

랩은 신호등을 지나친 횟수로 센다. `race_fsm.py` 는 `WAIT_GREEN` 상태에서만
`_record_traffic_encounter` 를 건너뛰므로, **출발 신호는 `WAIT_GREEN` 이 소비할
때만 랩으로 세어지지 않는다.** `LANE_DRIVE` 로 시작하면 첫 신호등 목격이 곧바로
1랩이 되어 FINISH 가 한 바퀴 일찍 뜨고, 그 뒤로는 `FINISH requires zero output`
으로 조향·속도가 0 으로 고정된다.

실전 런치 `module_drive.py` 는 `mode` 기본값이 `0` 이라 문제가 없지만,
**`module_drive_bag_test.py` 는 기본값이 `1`** 이다. 그래서 이 러너는 기본값을
`MODE=0` 으로 두고, 리포트도 `laps counted` 줄과 신호등 통과 목록으로 어느 쪽이
쓰였는지 항상 보여준다.

## 여러 bag 을 한 번에 — 배치가 바뀌어도 되는지

본선에서는 고정장애물 위치·좌회전 신호 타이밍·라바콘 배치가 모두 달라진다.
한 bag 에서 통과하는 것으로는 아무것도 보장되지 않으므로, 배치가 서로 다른
녹화들에 같은 판정을 돌리고 **여러 녹화에서 반복되는 findings** 만 따로 뽑는다.

```bash
ros2 run drive_eval run_stack_sweep.sh
BAGS="rosbag2_shortcut_1:1 rosbag2_straight:1" ros2 run drive_eval run_stack_sweep.sh
```

`BAGS` 항목은 `<bag 이름>:<초기 모드>` 이고, 기본 목록은 카메라가 충분한 속도로
들어있는 bag 만 고른다 — `/resized_image` 가 5 Hz 밖에 없는 녹화는 `lane_node`
가 굶어서 스택 판단이 아니라 입력 부족을 재게 된다.

이미 돌려 둔 결과만 다시 모으려면:

```bash
ros2 run drive_eval drive_eval summary --runs ~/drive_eval_runs/sweep_20260825_015539
```

### `run capture` 판정을 먼저 본다

첫 스윕에서 이전 실행의 노드가 살아남아 **`main_node` 가 6개** 동시에 같은
토픽에 발행했다. 40초 녹화에 모드 전환 2508회 같은 값이 나왔는데, 겉보기엔
데이터처럼 보여서 그대로 믿기 쉬웠다.

그래서 러너는 워밍업 뒤 `main_node` 개수를 세어 1개가 아니면 **녹화를 시작하지
않고 실패**하고, 채점기도 `/mode_info` 발행 주기가 50 Hz 제어 주기(`control.py`
의 `CONTROL_PERIOD_S`)를 크게 넘으면 `run capture` 를 FAIL 로 놓고 나머지 수치를
믿지 말라고 먼저 말한다. 발행자 수는 주기로 드러나므로 이 검사는 거짓말하지 않는다.

## 이미 기록해 둔 실행을 채점하기

```bash
ros2 run drive_eval drive_eval evaluate \
  --source-bag ~/my_rosbag/rosbag2_2026_08_13-13_33_23 \
  --run-bag ~/drive_eval_runs/run_20260825_010000/outbag \
  --json report.json
```

`/scan` 안의 라바콘 구간만 먼저 보고 싶으면:

```bash
ros2 run drive_eval drive_eval cones
```

## 무엇을 어떻게 재는가

### 시간축 맞추기

스택은 `ros2 bag play --clock` 이 주는 bag 시간으로 판단하지만, `ros2 bag record`
는 벽시계로 도장을 찍는다. 그래서 실행 bag 에 `/clock` 을 같이 기록하고, 그
`(벽시계 수신시각, bag 시간)` 쌍으로 두 축을 잇는다 (`timebase.py`).
재생 배속이 1.0 에서 벗어나면 타이밍 결론이 무의미하므로 리포트가 먼저 그것을
`playback` 판정으로 걸러낸다.

### 레이스가 끝난 뒤는 채점하지 않는다

이 bag 은 연습 주행이라 3바퀴를 마친 뒤에도 사람이 계속 돈다. 스택은 3랩에서
FINISH 로 가고 출력을 0 으로 고정하는 것이 계약이므로, 그 이후를 같이 채점하면
정상 완주가 "주행 포기" 로 읽힌다.

그래서 `/object_info[0]` 의 신호등 통과를 `TrafficEncounterGate` 와 같은 규칙으로
묶어 랩을 세고, 3랩을 채운 뒤의 0 출력은 **완주로 인정하고 채점 창을 거기서
끊는다.** 3랩을 못 채운 채 멈췄다면 그때만 `finishes the course` 가 FAIL 이다.

### 라바콘 구간 정답

`cone_truth.py` 가 `/scan` 에서 직접 만든다. `rubbercone_node` 와 **같은 탐색
범위**(1.10 m, ±85°, 좌우 0.85 m)를 쓰되, 판정 규칙은 일부러 다르게 — 콘 크기
클러스터를 찾아 **좌우 양쪽에 하나씩 있으면 통로**로 본다. 채점 대상 코드가
만든 정답으로는 그 코드가 놓친 구간이 보이지 않기 때문이다.

종료 판정은 연속 4 스캔 공백으로, `rubbercone_end_missing_frames=4` 와 같은
인내심을 쓴다. 한 스캔 놓쳤다고 구간을 쪼개지 않는다.

### 조향각

사람이 스틱으로 몬 기록이므로 **정확히 같아야 하는 것이 아니다.** 같은 순간에
같은 방향으로, 비슷한 크기로 꺾는지를 본다.

- `dir-agree` — 기록 조향이 5° 이상인 구간에서 좌우 방향이 일치한 비율.
  직선 구간의 0 근처 값까지 세면 잡음에 점수를 주게 되므로 제외한다.
- `r` — 두 조향 신호의 상관계수. 기준 0.35 가 사람 조향 상대로 달성 가능한지
  따로 확인했다: 같은 이봉분포 기준 신호에 대해 위상만 맞는 매끄러운 추종기는
  0.594, 그 기준 신호를 저역통과한 것만으로도 0.456 이 나온다. 즉 0.35 미달은
  기준이 가혹해서가 아니라 위상이 실제로 어긋난 것이다.
- `lag` — 상호상관이 가장 높아지는 시간 이동량. "제대로 꺾지만 0.3 초 늦다" 와
  "잘못 꺾는다" 는 RMSE 가 같아도 고쳐야 할 곳이 다르다.
- `amp(cand/ref)` — RMS 비. **맥락으로만 읽고 판정에는 쓰지 않는다.** 이 bag 의
  사람 조향은 라바콘 구간에서 중앙값 1.5°에 표본의 27~33% 가 풀락 100° 인
  이봉분포라, RMS 가 스파이크에 끌려간다. 같은 구간에서 스택은 평균 19°·최대 44°
  로 계속 꺾는데도 비율은 0.31 로 나온다 (자기 제한인 45° 에 닿지도 않는다).
  이 숫자를 "거의 안 꺾는다" 로 읽으면 엉뚱한 파일을 고치게 된다.
- `|angle| med / p90 / max` — 스택과 기록을 각각 분위수로 보여준다. 조향 크기
  판정은 사람과의 비율이 아니라 **90 분위 절대값 5°** 라는 바닥으로 한다.
- `saturation` — 조향 한계값에 붙어 있는 명령 비율. 상관계수가 높아도 두 개의
  구형파가 겹친 것뿐일 수 있다.

라바콘 구간 안/밖을 나눠서도 따로 낸다.

### 모드 전환

`/mode_info` 는 계단 신호이므로 **에지**만 본다. `race_fsm.py` 에 선언되지 않은
전환이 나가면 표시하고, 라바콘 통로마다 `CONE_DRIVE` 진입 지연·이탈 시점·구간
커버리지를 낸다. 통로가 없는데 들어간 `CONE_DRIVE` 는 따로 모아 보고한다.

## 판정 기준

`evaluate.py` 의 `Thresholds` 에 모아 뒀다. 사람 주행과의 **일치도** 기준이지
주행 품질 기준이 아니다.

| 항목 | 기준 |
|---|---|
| `dir-agree` | ≥ 65% |
| 상관계수 | ≥ 0.35 |
| 조향 크기 | 명령의 90 분위 `|각도|` ≥ 5° |
| 조향 포화 | ≤ 35% |
| 라바콘 진입 지연 | ≤ 2.50 s |
| 라바콘 구간 커버리지 | ≥ 50% |
| 라바콘 통로 신뢰 최소 길이 | 3.00 s (이보다 짧으면 표시만 하고 FAIL 시키지 않음) |
| 미주행 방치 | ≤ 10.00 s (3랩 완주 후는 제외) |
| 재생 배속 | 0.90 ~ 1.10 |

짧은 통로를 FAIL 로 올리지 않는 이유는, `/scan` 만으로는 2초짜리 라바콘 게이트와
좌우에 놓인 장애물 차량 두 대를 구분할 수 없기 때문이다. 오탐이 섞이면 리포트를
무시하게 되는 쪽이 더 큰 손해다.
